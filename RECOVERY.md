## Estado actual

Fases 1-25 completadas ✅. Última iteración: **All-in EV calc** (6ª sub-tab de `/calculadoras`, icono `Bomb` entre EV con fold equity e Implied Odds). Cierra el item 11 diferido de fase 24 — el cuarto Excel del usuario ("NUMBERS WE NEED TO ADD IN WHEN SHOVING OVER THE TOP PREFLOP"). Decisiones clave:

1. **Breakeven F% analítico, no Solver**. El Excel del usuario tiene "does NOT auto-populate. Use Solver to generate the answer" porque escribir la fórmula en C7 crea referencia circular (EV depende de F, F depende de EV). En nuestra implementación despejamos `EV = 0` analíticamente: `F·A + (1−F)·B = 0 ⟹ F* = B/(B−A)` con `A = Pot, B = Eq·(Pot+Shove−Call) − (1−Eq)·Shove`. Sin ciclo, sin Solver, siempre fresco. El 66% que muestra el Excel era una corrida vieja — nuestro analítico devuelve 56.1% con los mismos defaults (Pot=$100, Call=$75, Shove=$400, Eq=33%).
2. **Raw breakeven + UI handler de 4 casos**. `allInEv()` devuelve el F* crudo (puede ser negativo, >100, o null). La UI lo interpreta: negativo → "+EV en cualquier fold equity (incluso si nunca se tira)"; >100% → "imposible: incluso con 100% de fold no se cubre el showdown negativo"; null (denom ≈ 0) → "sin solución finita"; dentro de [0,100] → caption con el valor. Más informativo que clamping silencioso.
3. **Sensitivity table local, sin chart de barras**. El Excel tiene una gráfica de 13 columnas (−10B/−10F/−10E/−5B/−5F/−5E/Actual/+5E/+5F/+5B/+10E/+10F/+10B). Implementé `SensitivityTable` como `<table>` HTML con `overflow-x-auto`, columna Actual con `ring-1 ring-accent`, celdas tonal `emerald-300 / rose-300 / content-muted` por signo. Sin recharts ni librería de chart — el formato grilla numérica cubre la información sin overhead. Clamp [0, 100] en equity y folds para evitar valores físicamente imposibles cuando los inputs están cerca de los bordes.
4. **Convención: shove total incluye el call**. El hint debajo de "Cuánto shoveás" lo aclara — el Excel usa $400 como shove total cuando el call sería $75 (no $400 adicional al call). La fórmula `(Pot + Shove − Call)` resta el call para no doble-contar lo que el villano ya tenía en el bote. Verificado: 0.66·100 + 0.34·0.33·425 − 0.34·0.67·400 = $22.57 ✓ (D9 del Excel exacto).
5. **TS strict narrowing**. Inicialmente usé `const allValid = a !== null && b !== null && ...` afuera del `useMemo` pensando que TS narrowing alcanzaría, pero `noUncheckedIndexedAccess` + el callback fresco del `useMemo` rompen el flow analysis dentro del closure. Cambié a early-return dentro del `useMemo` con `if (a === null || b === null || ...) return null;` que es el patrón ya usado en `EvComplexCalc`. `allValid` queda solo para el `substituted` ternary fuera del callback (ahí sí narrow funciona).
6. **HomePage propagation**. Convención `feedback_calculators.md`: cada calc nueva propaga a HomePage (module card + FAQ + `aPlain`) en el mismo commit. Editado: line 78 "Cinco" → "Seis herramientas", line 240 FAQ JSX con descripción completa, line 257 `aPlain` plano sincronizado.

## Decisiones de diseño clave

Orden cronológico ascendente. Cada bloque captura el **por qué** detrás de algo no-obvio leyendo el código.

### Editor (fase 4)
- **History**: `{ ranges, activeRangeId }[]` en store, NO persistido, cap 50, snapshot por sesión de drag (no por celda). `pushHistory()` lo llama el UI antes de cada mutación imperativa (create/duplicate/delete/rename/group).
- **WeightSlider** global en toolbar (step 5). weight=100 → reemplaza celda; weight<100 → acumula hasta sum≤100 (trunca al hueco, no reduce otras acciones).
- **RangeCell** siempre aplica `CATEGORY_BG`; `buildBackground` usa weights como % absolutos y mete `transparent` trailing si sum<100. Siempre devuelve gradient (un color sólido en `backgroundImage` es CSS inválido).
- **Keyboard listener** a nivel window en EditorPage ignora input/textarea/contenteditable (permite undo nativo en inputs).
- **Selectors**: subscribir a `s.ranges` (ref estable) + `useMemo` — el shim de `useSyncExternalStoreWithSelector` invalida memos por identidad si pasás `useShallow` sobre `.map(r => ({...}))`.

### Viewer/Trainer (fases 5-6)
- **Filtros viewer/trainer NO persistidos**: abrir app debe arrancar sin sesgo. Compare state (toggle + B id) tampoco persistido.
- **`viewerRangeId` y `trainerRangeId`**: en uiStore, nullable, default null, sin bump de versión. Auto-selección del primer rango si el id persistido es stale.
- **Compare**: en compare mode el sidebar derecho desaparece; cada `RangePanel` lleva sus propias stats/legend.
- **Sampling clásico**: P(hand) ∝ combos del hand (no ∝ peso de celda) — reproduce frecuencia natural de reparto. Acción esperada por draw muestreada de los pesos de la celda con FOLD residual. Hands fuera del rango: implícito FOLD.
- **Drawing trainer**: comparación binaria in/out por combos (Jaccard). Cualquier acción en la celda truth la cuenta como "in".
- **Score session NO persistido**. Switching range → reset; switching hand → score continúa.

### A11y / UX (fase 7)

- **Menus** (Export, RangeManager): ArrowUp/Down/Home/End/Tab nav, focus al primer item al abrir, restore al trigger en Escape.
- **ErrorBoundary**: class component envolviendo `<RouterProvider>`, fallback con botón Reload, log a console.error SOLO en DEV.

### Push/Fold trainer — Nash HU (fase 18)
- **Por qué Nash HU only**: el chart fuente del usuario es la tabla canónica heads-up (BTN push, BB call). 6max position-vs-position multiplicaría el dataset por ~10× y requiere selector de posición — quedó fuera del scope acordado. La utilidad pedagógica está en endgame de torneo / SnG, donde HU push/fold concentra ~80% del valor.
- **Encoding row-major en `nashTable.ts`**: la primera transcripción intenté hand-by-hand (`AKo: 20, KQs: 20, ...`) y caí en errores sistemáticos al mapear offsuits (tenía `87o = 20` cuando la imagen mostraba `14.7`, `65o = 20` cuando es `2.4`, etc. — la confusión venía de que la posición de la celda en la imagen vs el orden canónico high-low del nombre del hand no es trivial). Solución: encodear en formato 13×13 row-major **idéntico a la imagen** y dejar que `gridCoordsToHand(r, c)` derive el nombre. Imposible equivocarse — el TS object literal se lee posicionalmente igual que el chart fuente. Único cell aproximado: `92s` (col 2 de row 9 no era legible en la imagen, puesto a `3.0`).
- **Convención de threshold**: `0` = nunca push/call (no se omite la key — eso rompería `noUncheckedIndexedAccess`), `20` = saturación / siempre push/call dentro del rango estudiado. La estructura mantiene 169 keys completas en cada chart así el predicado queda limpio: `shouldPush = bb <= push[hand] && push[hand] > 0`.
- **Footnotes `*63s`/`*53s`/`*43s`**: el chart fuente marca exclusion bands ("63s push outside 2.4-5.0 BB") — son rangos donde Nash dice no pushear aunque hands más débiles sí. No están modeladas en código (`shouldPush` solo usa el upper bound). En la práctica son cells de borde poco frecuentes y modelarlas requiere cambiar la signatura del helper a algo tipo `pushBandOf(hand): { upper: number; gap?: [number, number] }`. Diferido.

### Fix SEO indexación GSC (fase 19)
- **Por qué el sitemap mismatch causa "Error de redirección" y no es un 301 inocente**: GSC interpreta la URL sometida en sitemap como **declaración de URL canónica**. Si esa URL siempre redirige (vía 301), Google la marca como "URL alternativa con etiqueta canónica adecuada" en el mejor caso o "Error de redirección" si el destino tiene canonical incoherente. El error en `/viewer` se disparó porque `/viewer/` declaraba canonical=`/` (la home) en lugar de canonical=`/viewer/`, así que el 301 desde `/viewer` apuntaba a una página que decía "no soy yo, soy la home" — Google rechazó indexar la URL.
- **Por qué el canonical estático en `index.html` no se quita**: queda como **fallback** para crawlers que no ejecutan JS (los pocos que quedan en 2026). Googlebot post-2018 ejecuta JS y respeta el canonical actualizado por `useDocumentTitle`. La estrategia es "default seguro en HTML estático, override correcto en runtime". Si en algún momento se mueve a SSR/SSG, el default se podría refinar al pre-render — pero hoy con SPA puro el patrón actual es la implementación correcta.
- **Por qué NO usar `disallow` en robots.txt** para las URLs sin barra: sería palanca agresiva que también bloquearía el 301 mismo. Google no podría seguir el redirect ni leer el canonical correcto. La consolidación natural vía 301+canonical es más limpia y se completa en 2-4 semanas.
- **Por qué Google ya había indexado `/viewer/` correctamente** antes del fix: cuando Google detecta que el contenido del canonical declarado (`/`) es **distinto** al de la URL inspeccionada (`/viewer/`), ignora la declaración del usuario y elige la URL inspeccionada como canónica. Eso explica por qué la captura de "Páginas indexadas" mostraba `/viewer/` indexada con "Seleccionada por Google como canónica: URL inspeccionada". Google siendo tolerante. Pero esa señal cruzada con el 301 desde `/viewer` (que apuntaba a una página con canonical=`/`) es lo que disparó el error específicamente en `/viewer` — dependiendo del orden de crawl.
- **Pasos manuales en GSC tras el deploy** (documentados para futuras sesiones que toquen el sitemap o las rutas SPA): re-enviar sitemap (campo "Añadir un sitemap" → URL absoluta `https://rangesoprano.com/sitemap.xml` — el path relativo ya no es aceptado), validar el bucket "Error de redirección" (botón en el reporte), y "Solicitar indexación" en Inspección de URLs para cada una de las 3 SPA con barra. La validación corre en background 1-7 días; aunque se haya disparado **antes** del deploy del fix, no causa problema porque Google evalúa el estado actual de la URL al re-rastrear, no el estado del momento del click.
- **Falsos positivos a ignorar en GSC**: `http://rangesoprano.com/` listada como indexada es artefacto histórico (HTTPS ya está forzado vía 301 server-side desde antes de fase 18). Google la deindexa sola en el siguiente crawl, no requiere acción.

### Randomizador en /viewer Resumen (fase 20)
- **Por qué tarjeta fija en `actions` del PageHeader y no panel collapsable inline**: la primera implementación fue un panel grande arriba del grid de OverviewTiles que el user mismo identificó como ruido visual ("estorba los rangos"). El recuadro azul que dibujó en una captura apuntaba al espacio vacío entre el título "Resumen" y el borde derecho — exactamente el slot `actions` del `PageHeader`. Reusarlo en lugar de inventar una zona nueva mantiene la coherencia con cómo el resto de la app rellena ese espacio (botones de Imprimir, etc.) y deja la prioridad visual en las tablas.
- **Por qué el popover de configuración es `absolute` y no inline**: el user fue explícito — "el funcionamiento del randomizador no debe salir del recuadro azul, pero la configuración sí puede tapar momentáneamente". Se traduce en: la card principal nunca empuja layout (height fijo), y el popover se monta como `absolute right-0 top-full z-30` para overlay. Click outside o `Escape` lo cierran. Eso protege el flow durante el juego (las tablas siempre visibles) y solo permite intrusión cuando el user explícitamente pidió cambiar algo.
- **Por qué se descartó "Vincular rango"** tras llegar a estar implementada: el feature pedía 5 clicks por mano (abrir ⚙ → toggle vincular → dropdown rango → seleccionar → click celda) para resolver una decisión que el user ya estaba tomando visualmente en ~1 segundo (mira el OverviewTile, lee el roll, mira qué preset se iluminó verde). Es un caso clásico de "valor conceptual ≠ valor de uso". El user mismo lo cuestionó en mesa real y propuso click-on-cell directo en los OverviewTiles; respondí que rompía la affordance "click tile → abrir Individual" y que el flujo manual era ya más rápido. Borrarla limpió ~80 líneas (componente `RangeLinkedMode` + helper `evaluateAgainstCell` + estado `linkedMode`).
- **Por qué la lista de N rolls también se descartó**: el randomizador genérico de la imagen de referencia ("Poker GTO Randomizer PRO") la incluye porque no sabe qué hacer con varios presets a la vez. Range Soprano sí: los 4 presets simultáneos cubren múltiples splits contra UN solo roll. Forzar correspondencia 1-a-1 entre N rolls y N presets sería arbitrario y confuso. El user lo planteó textualmente ("¿qué utilidad les puedo dar?") y la conclusión fue quitarla. Liberé el field `listSize` del schema Zod sin bumpear version: cambié `.strict()` por default (strip silencioso) para que payloads v1 con `listSize: 1` se hidraten limpios sin perder sets/frequency.
- **Auto-label inteligente en `updatePreset`**: cuando el user cambia el `value` de un preset, el helper detecta si la `label` actual sigue el formato auto `${v}/${100-v}` y la regenera. Si la label fue editada manualmente (ej. `"Open Raise"`), no se toca. Heurística simple — `wasAutoLabel = p.label === autoLabelFor(p.value)` antes de mutar — que respeta la intención del user sin agregar un flag explícito "manualmente editada".
- **Toggle Eye/EyeOff del highlight verde**: el user pidió poder desactivar el resaltado verde cuando solo quiere ver el número. Implementación: campo `highlightEnabled: boolean` con `.default(true)` en el schema (compatible con persisted v1 sin bump), botón en la fila del Set tabs al lado del gear con icono `Eye`/`EyeOff` de lucide. El render del `PresetChip` recibe `matched={highlightEnabled && lastValue !== null && lastValue <= p.value}` — si el toggle está OFF, ningún chip se ilumina aunque haya match. Mismo lenguaje cromático que el resto: `border-success/60 bg-success/15` para activo, `border-border bg-surface/40` para inactivo.
- **Auto-loop con frecuencia configurable**: patrón `setInterval(rollRef.current, frequency)` con `useRef` para no recrear el intervalo en cada render. Apagar el modo Auto al colapsar el panel — diferí la decisión inicial pero después la quité porque el panel es siempre fijo (no colapsable). Hoy solo se apaga si `autoEnabled === false` o el componente se desmonta.
- **`zPersistedRandomizerState` sin `.strict()`**: tras la fase 20a (cleanup), un `listSize` legacy en localStorage hubiera fallado el `safeParse` y forzado fallback a defaults — los sets editados del user se perderían. Quitar `.strict()` permite strip silencioso de fields removidos. Convención: para schemas de persist con evolución esperada, evitar `.strict()` y aceptar que keys extra son válidas.
- **Portabilidad en `.json` via `zExportPayload.randomizer`**: extender el payload existente (que ya tenía `groupMeta.optional()`) con `randomizer.optional()` referenciado por `z.lazy()` para resolver la dependencia hacia adelante (Zod evalúa `zExportPayload` antes de `zPersistedRandomizerState` en el archivo).
